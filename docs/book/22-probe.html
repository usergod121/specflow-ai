② 上下文：告诉开发"改哪儿、为什么"

这一格交四样东西，其中 changes 是 ④ 的写白名单——它直接决定开发能碰哪些文件。

先存需求，再跑探针

Api.probeBrief {requirement, design} └ FlowService.note(PROBE,{requirement,design}) 需求与设计进 facts，可随时改 Api.probeAgent ├ requireReachable(PROBE,"跑探针") ├ Runs.start(PROBE,"probe-agent") └ body: Probe.run() ├ Loop 跑 read_list / read_file（只读） ├ 交回四样：files / changes / context / prompt ├ Probe.validate 三条： │ files 必须真存在（读不存在的文件＝在猜） │ changes 里"已存在"的必须先出现在 files 里（能改的先得能读） │ changes 里"还不存在"的放行（那正是要新建的） ├ 过 → Atomic.write(layout.probe(id), 四样) ← 旧产物这时才被覆盖 └ 不过 → REJECTED，旧 probe.json 一个字节不动

四样产物到底是什么意思

栏语义谁在用它
files开发要读的文件（必须真存在）④ 提示词“先读这几处”
changes写白名单：要改的 + 要新增的Whitelist 包住两个写工具；也决定轮次预算
context为什么这些地方相关（人写的交代）④ 提示词第二段
prompt这一轮要做什么（不许空）压缩时原样保住的那份任务书

另外两个按钮

Api.probeView 读回盘上那份；Api.probeSave 存人改过的四样——三栏（files/changes/context） 字符串或数组都认，避免界面提交字符串时被清成空数组。

闸：files 非空 且 prompt 非空。
常见失败：只列了“要改”没列“要新增”（④ 因此建不出文件）；往 files 里塞还不存在的路径（被驳回并提示只放 changes）。
