第 0 部分

需求

0.1 要解决什么问题

给一个已有的项目和一个"要改什么"的需求，目前的做法是：人自己搭环境、自己读代码、 自己想验收标准、自己写代码、自己跑测试——每一步都在反复切换身份，而且"验过了"这三个字 没有任何证据支撑。

这个系统把这件事拆成五个有闸的站点，让每一步都有产物、有判据、有留档：

① 环境项目跑在什么容器里、怎么起、能不能构建
② 探针读项目，交出「改哪儿、怎么改」的上下文
③ 用例把一句模糊需求变成可逐条验收的清单
④ 开发在白名单内改真项目代码，每次交差编译一次
⑤ 测试在副本 + 真容器里逐条验，结论与证据写回清单

0.2 硬需求（这一版不许违反的）

#需求为什么它是硬的
R1五站语义与顺序不变它是"卡在哪一站"的唯一答案来源；一变，所有历史留档都失去意义
R2一个 bat 入口（起 / 停 / 销毁）用户明确要求"别让我自己敲命令"
R3前端尽量少改，只许加流式与必要按钮时间与风险都不允许重做界面
R4状态是人能打开看的文本排错时这一条比任何查询语言都值钱
R5不碰用户自己的旧实例（8770）那是他正在用的东西

0.3 非目标（刻意不做）

  • 不做全能 Agent：不让模型决定"下一步做哪一站"。顺序写死，模型只负责站内那一段活。
  • 不做多智能体群聊：五站已经是编排；自由对话会让"卡在哪"失去答案。
  • 不换数据库：事件流 id ≡ 行号 + 人能打开看，是这套东西最值钱的性质。
  • 不把引擎自己塞进容器：引擎要调 docker 造沙箱，给了 docker.sock 就等于给了宿主 root。

0.4 什么叫"跑通了"（验收口径）

  1. 端到端：真模型 + 真 Docker，五站从"起环境"走到"接受"，且 ④ 的成果由独立脚本核对（不采信 Agent 自述）。
  2. 单元与模块：闸、用例状态机、预算、守卫、事件流、断点、压缩、路由形状，每条都有测试。
  3. 界面：七个路由在真浏览器里零控制台错误、零失败面板；事件走 SSE。
  4. 收场：容器与卷能被一条命令收干净，且不动别人的东西。

第 1 部分

认识这个系统

1.1 一句话

给它一个项目 + 一句需求，它自己把五站跑完；每一站都有闸，上一站没冻结，下一站连点都点不动。

1.2 三层核心认知

第一层：它是流水线，不是全能 Agent

Agent 只是流水线上那几站的"手"。站序、每站产物、站与站之间的闸都不由模型决定。 这一条是整个系统可解释性的来源。

第二层：闸是纯函数

// flow/Gate.java —— 一格一个实现，签名只有这一行
String blocked(Facts facts);   // 空串 = 能做；否则就是直接给用户看的那句话
实现里不许读盘、不许看时间、不许写事件——同一份 Facts 永远给同一个答案。 于是闸能被单测钉死，而界面上的"为什么还不能点"与 409 的正文是同一句话。

第三层：状态是文件，事件是流水账

flow.json五格状态 + 每格产物（原子替换写）
events.jsonl唯一归档日志；行号 = 事件 id
cases.json / probe.json / summary.md人能直接改的产物

1.3 三条铁律 + 六条不变式

铁律（EventLog）意思
只有一个写者日志、工具调用、闸、收场，全从 append() 出去
id 恒等于行号追加前现读行数、盖号、写一行 → 游标与"第几条"是同一个数，重启接着数
盘上是唯一真相内存里那份只是副本，用 (大小, mtime) 校验，对不上就整份重读
不变式违反会怎样
事件只有一个写者两个写者各数一套 id → 界面拉取时重复或跳过（v2 之前就这样）
Event.id ≡ 行号重启后历史错位
一个事实只有一个名字（Facts 常量）写的人写 envConfirmed、读的人读 envReady → 闸永远看不见
Layout 是唯一路径权威四处各拼一遍字符串，必有一处少一层目录
长任务只从 Progress 一个口说话两条进度通道 → 界面读不到（用户原话"只听到风扇转"）
改完必须读得回来：人能改的东西落在盘上之后，下一处要现读，不许用"启动那一刻的快照"改了没反应（② 的上下文白写、编译命令"还是空的"），而且零报错——见 5.11

2.5 顶层抽象：整件事只有八个概念

先说结论：这个系统里人需要理解的东西只有八个。看懂这八行，剩下的都是它们的组合； 记不住这八行，读一万行代码也只是记住了一堆细节。

#抽象一句话它替人回答的问题不变量
1五格 Node / State流程是五级台阶，一格一格冻住「我现在走到哪、下一步能不能点」LOCKED → READY → DONE，只有三态
2闸 Gate / Gates / Facts能不能点只由一处判据回答，答不出来就说清差哪一步「为什么我点不动」闸是纯函数；前端一行判闸逻辑都不许有
3账本 Event / EventLog发生过的每一件事只有一条追加的记录「刚才到底发生了什么」单写者；id ≡ 行号；盘是真相
4产物 probe.json / cases.json / summary.mdAgent 的产出是人能打开、能改的文件「它到底交了什么」一份产物只有一个落点（Layout）
5环 Loop / Tool / Protocol问模型 → 认它的动作 → 跑工具 → 结果喂回去「Agent 是怎么干活的」一次调用恰好一前一后两声；工具坏了不崩循环
6预算 Budgets / LoopLimits / CaseBudget「我愿意等多久」「一条用例花几次」写成数，不散在各处「为什么它停了」一个旋钮一个语义（时间 / 轮次 / 次数）
7守卫 CommandGuard / Approvals谁能动手、动手之前问不问人「它会把我机器搞坏吗」自动拒 > 问人 > 放行；三档各有固定话术
8沙箱 TestSandbox / Compose被测项目跑在副本 + 容器里，跑完连卷一起收「它会不会弄脏我的项目」只挂副本；down -v 一定执行

它们怎么拼起来（一次「点按钮」的完整旅程）

人点「跑测试」

  ├─① 路由层  Api.testRun()            // 只做：取参数 → 调下层 → 拼响应
  │    └─ 闸  FlowService.requireReachable(TEST)      ← 抽象 2

这八个抽象各自的"代价"（写的时候真付过的）

抽象如果不这么做代价（我们真付的）
五格 + 闸用户点不动却不知道为什么，只能把五格各点一遍每加一个门槛要同时改闸与话术（所以闸拆成"一格一个实现 + 一张表"）
账本（单写者 + id≡行号）两个写者各数一套 id → 界面重复/跳过、重启后历史消失写事件必须同步、不许并发写；读要过 (size, mtime) 缓存
产物放盘上Agent 的结论只活在内存里，刷新就没了，人也没法改每样产物一份 Layout 方法；读它要处理"文件不在"
环（ReAct）一次性长提示词 → 一出错就整轮重来协议要自己解析（Protocol）+ 认不出来要补问 + 打转要打断
预算集中「改超时」只回显不生效（v2 的真事故）三个尺度要分清：时间 / 轮次 / 调用次数，混了就互相打架
守卫三档要么什么都问（187 秒白等），要么什么都不问（危险）要维护"哪些算危险"的正则名单，且每条都要有反例测试
沙箱Agent 直接改你的项目、跑你的环境每轮复制一份项目、起一个容器（贵），所以才有"依赖缓存卷"这条补救

第 3 部分

契约与 API

3.1 五格状态机

LOCKED
→
READY
→ 冻结 →
DONE
LOCKED  前置没冻结：连点都点不动（409 + 一句话）
READY   这一格可以做活了，但还没冻结 —— 每次读都现推，不落盘
DONE    冻结了：下游随之解锁；回退会把下游一起作废
为什么 READY/LOCKED 不落盘：落盘就会"过时"。每次现推的代价是读一次 flow.json， 换来的是状态永远不骗人；只有 DONE 是记下来的（它代表"人确认过"）。

3.2 用例状态机（③ 的产物 → ⑤ 的结论）

生成时：  PENDING
验完：    PENDING → PASS（必须有证据原文）
        PENDING → FAIL（说清哪里不对）
        PENDING → ERROR（说清为什么没测成）
预算用尽：PENDING → SKIPPED（终态，但不是结论；可「重试这一条」）
重试：    SKIPPED / FAIL / ERROR → PENDING（只重验这一条）
提交时的五条机器判据：① 清单非空 ② 没有 PENDING ③ PASS 有证据 ④ 非 PASS 有原因 ⑤ 至少一条真结论——全是 ERROR 等于"没验"，把它当通过等于把"没验"说成"没问题"。

问题答案
谁在压Loop（每轮开头第一件事），所以五格 Agent 全都压
锚点表谁来写循环自己攒「读过/改过的路径 + 最近的失败」，调用方只补「进度」那几句（②③④ 原来一句都没有——见 §9 第 5 条）
能不能压很多次能，而且必须：一段长运行会压好几次。所以要认头（system + 第一条不是自己插的 user 消息 = 任务书），否则第二次就把需求扔了（§9 第 6 条）
压了看得见吗看得见：事件流里一条 warn「上下文压到 N 条（原来 M 条），X 字符（原来 Y 字符）」
为什么不调模型写摘要多一次延迟、多一次花钱、多一个"摘要本身错了"的故障点；而要保住的只有三句，引擎自己就知道 → 同一段对话永远压出同一份（可单测）
两道闸不是一回事：单条工具输出先被截到 2 万字符（MAX_OUTPUT_CHARS）， 这是单价上限；整段对话超过 6 万才压，这是总量上限。两个都要有—— 只有单价上限的话，30 条 2 万字符的结果照样能堆成 60 万。

git commit -m "…" 里带 "提交静默失败，而 tag 已经打上（看起来提交成功）提交信息只用 「」；或者写进文件用 -F
mvn package 时报 "Unable to rename target/specflow.jar"jar 没更新，之后所有验证都在验旧包（真发生过一次，靠 jar 时间戳才发现）先杀 java 进程；每次验证前先看 jar 时间戳

判据永远在三处：docs/ARCHITECTURE.md（契约）、docs/API.md（接口）、 docs/DELIVERY.md（验过什么 / 没做什么）。这一本解释的是为什么长这样。
