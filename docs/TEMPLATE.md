# 怎么写一个模板

模板放在 `.specflow/templates/<名字>.yaml`，一个文件一份，**文件名就是模板名**。

---

## 一句话

**模板只装「项目那一侧的常量」——产物形态、技术栈、角色、代码风格、常用的参考文件。**

它**不装需求**。需求每次都不一样；写进模板，就等于「一个模板只能匹配一种需求」。

| 属于模板（配一次） | 属于每次运行（每次给） |
|---|---|
| 产物形态、技术栈、角色、代码风格 | 需求 |
| 默认上下文依赖 | 验收标准 |
| | 目标文件、本次补充的上下文、约束 |

所以配好一个「Spring Boot 后端」模具之后，**加接口、加方法、改逻辑、修缺陷都用它**，
不用给每种需求各配一个模板。

---

## 字段参考

```yaml
name: spring-backend          # 必填。同时是文件名；改名要连文件一起改
tags: [class, java, spring-boot, mybatis]
description: Spring Boot 后端通用模具
system: |                     # 必填。角色、做事方式、代码风格
  ...
context:                      # 可选。默认上下文依赖，本次可逐项移除
  - ref: src/main/java/com/demo/UserController.java
    note: 照这个已有接口的风格写
```

一共五个字段，两个必填。

## tags：标签

```yaml
tags: [class, java, spring-boot, mybatis]
```

标签里放两层东西，写法一样：

| 层 | 回答的问题 | 例子 |
|---|---|---|
| **产物形态** | 写出来的是个什么东西 | `class`、`interface`、`function`、`script`、`component`、`module`、`test` |
| **技术栈** | 用什么写 | `java`、`spring-boot`、`mybatis`、`mysql` |

引擎**不区分这两层**，一律当成「这个项目这一侧的约定」原样拼给模型。
这么做是刻意的：一旦引擎要去认哪些标签是「形态」，就得维护一份对照表，
而那份表永远抄不全——标签的价值在于「一眼扫过」，不在于被引擎理解。

**只写框架名就够了。** 写了 `mybatis`，模型自己就知道有 `@Select`——
我们不该去维护一份「标签 → 注解」的对照表，那是把训练数据抄一遍，而且永远抄不全。

引擎把它们拼成一段话，并补上优先级：

```
## 模板约定
class、java、spring-boot、mybatis

产出物的形态与技术栈以上面这组约定为准，可以直接使用其中的注解与标准封装类；
但具体的设计细节以本次需求说明为准。
```

**标签管「可以用什么」，需求管「要什么」，冲突时以需求为准。**

规则限制：

| | |
|---|---|
| 单个标签 | 不超过 24 个字 |
| 标签总数 | 不超过 12 个 |
| 去重 | 自动 |
| 白名单 | **没有**，打任何词都行 |

限量不是洁癖：标签一旦能塞下一整段话，它就变成**第二个提示词**，
而且是优先级说不清的那个。宁可在这里拦住。

界面上的输入框给了一份常见标签的提示（`class` / `function` / `script`，`java` / `spring-boot` / `mybatis` / `fastapi` …），
但只是提示，不强制——打任何词都算数。

## system：角色与做法

这是模板里唯一一段「话」。写三件事：

1. **角色** —— 你是一名排查缺陷的工程师
2. **做法** —— 先理解现象与期望的差距，再定位真正的原因
3. **边界** —— 修改要尽可能小，不要顺手改动其他代码

**不要在这里写需求。** 也别写「本次要实现 XXX」——那是每次运行的事。

**这里也不能写 `{{占位符}}`。** 模板是配一次、长期复用的静态文本；允许它写占位符，
就等于在界面上留一个「存得进去、一运行就报未赋值、而且**无从修复**」的死胡同——
界面上没有填变量的地方。要随每次变化的内容，写进需求。

---

## context：默认上下文依赖

模板可以声明「用这个模具时，通常还需要看到哪些现成的代码」。

```yaml
context:
  - ref: src/main/java/com/demo/UserController.java
    note: 照这个已有接口的风格写
  - name: 订单表结构
    text: |
      CREATE TABLE orders (id BIGINT, status VARCHAR(16))
    note: 库里的真实定义
```

两种形态，**给哪个就是哪个**：

| 形态 | 字段 | 什么时候读 |
|---|---|---|
| 引用文件 | `ref` | **每次运行实时读**——文件改了它跟着变，不会过期 |
| 内联文本 | `text` | 本来就写在这里，直接贴进提示词 |

`name` 可留空：引用形态会自动用文件名。
`note` 是给模型看的**为什么**，一句话就够——「照它的风格写」比什么都不写有用得多。

**每一条都可以在本次运行时单独移除。** 默认带了订单表结构，而这次跟订单无关？删掉它。

## 一个完整的例子

```yaml
name: spring-backend
tags: [java, spring-boot, mybatis]
description: Spring Boot + MyBatis 后端通用模具
system: |
  你是一名严谨的 Java 后端工程师。

  你只修改需求所要求的部分：不要顺手重构，不要调整无关代码的格式，
  不要引入新的第三方依赖，不要改变现有方法的对外行为。
  保持目标文件原有的命名与缩进风格。

  需求没写到的地方，跟随目标文件里已有的写法，不要自己另立一套。
```

就这么多。**没有需求、没有输入字段、没有产物类型。**

## 在界面上创建

模板下拉框里选 **「＋ 新建模板…」**，直接落到新建表单，光标在名字上。
也可以点「管理模板」→「新建」，两条路是同一段代码。

管理弹层里两个视图改的是同一份数据：

- **表单**：名称、标签（回车加一个，可删）、说明、角色提示词
- **源码**：完整 YAML，包含表单视图不放的默认上下文

保存前会校验，通不过不会落盘。**改了以后立刻生效**，不用重启服务。

模板名能用中英文、数字、下划线、连字符。**但不能以 `__` 开头**——
`__free__` 和 `__new__` 是下拉框内部用来表示「自由输入」「新建模板」的保留值，
拿它当模板名会让那个模板在界面上永远选不中。

## 常见错误

| 现象 | 原因 |
|---|---|
| `未知字段 user` | 模板不装需求，需求在运行时给 |
| `未知字段 type-name` | 已废弃，改用 `tags` |
| `缺少必填字段: system` | `system` 必填 |
| `模板名非法` | 名字只能用中英文、数字、下划线、连字符，不超过 64 字 |
| `标签过长 / 最多 12 个` | 见上文 |
| `角色提示词里不能有占位符` | `system` 里写了 `{{x}}`，模板不支持占位符 |
