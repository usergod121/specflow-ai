# 架构

## 一句话

模型负责语义（读懂需求、决定改什么），本地引擎负责确定性（能不能安全地改）。
两者之间用一套行级补丁协议连接，引擎对模型的输出**只接受、不猜测**。

## 分层

```
com.specflow
├── SpecflowCli            唯一入口，也是唯一的异常边界
├── cli/                   五条子命令 + 输出格式
├── web/                   本地 Web 界面
│   ├── WebServer          只做路由与异常翻译
│   ├── Http               收发与查询参数（纯管道）
│   ├── WorkspaceApi       模板与任务草稿的 CRUD
│   └── RunService/RunHub  运行编排与进度缓冲
├── agent/                 编排：重试、回滚、反馈、进度回调
├── context/               上下文组装；补丁协议文本
├── review/                检查阶段：流程图 + 缺失清单
├── history/               运行留档：记录、读写、录制器
├── task/                  任务草稿的读写
├── llm/                   OpenAI 兼容协议的 HTTP 客户端
├── template/              模板的读写、校验与查询
├── spec/                  spec 的数据模型、加载、语义校验
├── project/               项目级配置（构建命令、模型、快照）
├── patch/                 补丁协议：解析 → 定位 → 计划 → 落盘 → 差异
├── snapshot/              快照与回滚
├── verify/                校验器扩展点与编译校验实现
├── util/                  路径守卫、文件读写
└── exception/             四个业务异常
```

依赖方向是单向的：`cli → web/agent → {context, patch, snapshot, verify, template, project, spec, llm} → util/exception`。
`patch` 不知道 `agent` 的存在，`verify` 不知道模型的存在，`agent` 不知道 HTTP 的存在。
任何一层都可以单独测试。

## 两个入口，一套引擎

命令行和 Web 界面不是两套实现，而是同一个 `Spec` 的两个入口：

```
spec.yaml ──SpecLoader──┐
                        ├─► Spec ──► SpecValidator ──► Spec ──► DevelopmentAgent
浏览器表单 ──RunRequest─┘
```

`RunRequest` 是 `Spec` 的「表单版」，`toSpec()` 之后就再也分不出是哪边来的。
这样做的直接收益：**界面和命令行拒绝同一个补丁的理由永远一致**——
如果补丁定位规则改了，两边同时改变，不存在「命令行拦住了但界面放过去了」。

## 一次运行的数据流

```
spec.yaml ──SpecLoader──► Spec ──SpecValidator──► 合法 Spec
                            │
                            ▼
                 ContextAssembler ──► system(补丁协议) + user(需求+目标文件内容)
                            │
                            ▼
                        LlmClient ──► 一段含补丁块的文本
                            │
                            ▼
                  PatchParser ──► List<PatchBlock>
                            │
                            ▼
              PatchStrategy.plan ──► PatchPlan（已校验，未落盘）
                            │
                ┌───────────┴───────────┐
                ▼                       ▼
        WorkspaceSnapshot          PatchApplier ──► 磁盘
                │                       │
                └───────────┬───────────┘
                            ▼
                      Verifier（编译）──► 通过？收工 : 回滚 + 回喂重试
```

## 关键不变量

以下是这套代码存在的理由，改动它们等于换一套设计：

1. **校验与写入分离。** `PatchStrategy.plan` 不碰磁盘，`PatchApplier` 不做判断。
   因此「补丁有问题」和「磁盘有问题」是两类永远不会混淆的失败。

2. **计划是纯函数。** `PatchPlan.render(file, content)` 给定内容必然产出同样的结果，
   可以脱离文件系统做单元测试。

3. **换行符只在比较域统一。** 比较前抹平为 `\n`，写回时还原目标文件原有风格。
   Windows 工作区是 CRLF、模型永远回 LF，不处理这一条整个匹配逻辑就是废的。

4. **锚点必须唯一。** 命中多处时报错而不是取第一个。模型偶尔会给出只含一个 `}` 的锚点，
   取第一个匹配位置就会静默改错代码——这是最危险的一类失败。

5. **回滚先于重试。** 见下文。

6. **「跳过校验」不等于「校验通过」。** `VerificationResult.Status.SKIPPED` 与
   `AgentResult.Status.SUCCESS_UNVERIFIED` 都是一等公民，会明确打印出来。

7. **异常只在边界处理。** 内部各层一律直接抛 `SpecflowException`，不写 try-catch；
   CLI 是唯一的翻译点。业务代码里的 try-catch 只出现在「必须清理资源」的地方
   （临时文件、被中断的进程）。

## 两条重试预算

| 预算 | 触发条件 | 代价 | 上限 |
| --- | --- | --- | --- |
| 补丁冲突 | 锚点不存在 / 不唯一 / 重叠 / 越界 | 磁盘未改动，便宜 | `MAX_CONFLICT_RETRIES = 2` |
| 校验失败 | 编译命令返回非 0 | 已写盘又回滚，昂贵 | `spec.verify.max-retry` |

分开管理是刻意的：把两者合成一个计数器，会出现「锚点写错两次就把编译重试额度耗尽」这种事。

## 回滚先于重试

编译失败时的处理顺序是：**先回滚，再重试**，而不是「记住改动、在改动基础上修」。

因为模型不擅长追踪自己上一轮改了什么。若在已改动的基础上重试，模型必须推断出
「文件现在是我改完的样子」并且按新内容写 SEARCH 锚点——它经常做不到，于是第二轮
又给出按原始内容写的锚点，必然失配，重试预算就这么烧完了。

回滚之后，每一轮的起点都是「原始代码 + 需求」，锚点永远按原始内容写。代价是每轮
重发一次完整补丁，收益是重试真正有效。

## 提示词协议不可被覆盖

`ContextAssembler.systemMessage` 永远是 `PatchProtocol.INSTRUCTIONS + 模板的 system`。
模板可以改变模型「怎么想」，但不能改变引擎「怎么读」——
否则一份写错的模板就能让引擎的解析逻辑失效，而此时用户只会看到「补丁解析失败」。

## 扩展点

| 想加什么 | 实现哪里 | 需要改动 |
| --- | --- | --- |
| 新的落盘方式（AST 合并、结构化插入） | 实现 `PatchStrategy`，登记进 `PatchStrategies` | 不动 Agent / CLI / 校验层 |
| 测试校验（按需求派生用例并执行） | 实现 `Verifier`，加入 `RunCommand.verifiers()` | Agent 已经按列表顺序执行并在首个失败处停止 |
| 新的模型服务 | `LlmConfig.baseUrl` 换地址即可（协议兼容 OpenAI） | 不动编排 |
| 新的需求写法 | 往 `.specflow/templates/` 放一个 yaml | 不需要重新编译 |
| 新的进度展示（终端进度条、桌面通知） | 实现 `AgentListener` 传给 `DevelopmentAgent` | Web 界面就是这么加的 |

测试 Agent 的位置已经在架构里留出来了：它与编译校验在流程上的位置完全一样，
都是「写入之后、收尾之前的一段可失败检查」。`BuildConfig` 里的 `lint` / `test`
两个字段就是为它预留的。

## 当前项目是一个可替换的对象

服务起来时可以不带项目（进欢迎页），也可以在界面里随时换。做法是把「服务一个项目所需的那一堆
对象」收进一个 `OpenProject`：模板、草稿、文件索引、运行记录、项目配置全在里面。

换项目就是换一个 `OpenProject`——在收进这一个对象之前，它们是散在 `WebServer` 字段里的，
换项目就变成「记得把每一个都重建一遍，别漏、别错顺序」，漏一个界面上就会出现
「文件树是 A 项目的、模板还是 B 项目的」这种四不像。

两条纪律：

- **每个请求只读一次当前项目。** `route` 开头把 `open` 取到局部变量再往下传，
  这样换项目换到一半时，不会有请求一半用旧项目一半用新项目。
- **换项目要收掉旧的。** `OpenProject` 实现 `AutoCloseable`，因为里面的 `RunService`
  带一个运行线程池；不收就一直挂着，而它写进度的那个 `RunHub` 也没人再看了。

**有任务在跑就不许换**，也不做「切了就中断」——中断会丢掉已经改了一半的文件。

这道闸门本身要盖得住才有效。请求体是**先读完、再拿锁**的：`/api/run` 读完 body 之后会和
换项目抢同一把锁，先确认「我捕获的那个项目还是当前项目」，再把运行注册进去。
少了这一步，一个慢请求（body 几秒才发完）就足以让换项目挤在中间——旧项目的线程池被收掉，
随后那次提交落在一个已经关门的池子上：界面收到 500 和一串内部类名，
或者更糟，200 加一个永远不会开始的任务。

**换项目走走的是整页刷新**，不是就地替换界面。要换的东西太多（模板、文件树、草稿、进度），
就地更新只要漏一处就会留下四不像；刷新一次几百毫秒，换的是「状态一定干净」。

## 打开目录用系统自己的对话框

「打开文件夹…」弹的是 Windows 自己的文件夹选择窗口，而**不是页面里仿的一个**。
这不是风格取舍：浏览器不会把系统对话框里选中的绝对路径交给页面
（`<input webkitdirectory>` 和 File System Access API 都只给文件名），
页面自己弹的那个框拿不到用户真正选的是哪儿。

而这个服务本来就跑在用户同一台机器上（`LocalOnly` 保证了这一点），所以由它去弹：
`FolderPicker` 在 Windows 上走 PowerShell + `FolderBrowserDialog`，macOS 走 `osascript`，
Linux 走 `zenity`。请求会一直挂着直到用户选完，所以界面那边按钮要变成「正在等你选…」。

弹不出来（没有桌面的环境）就如实报错，并指向「手动输入路径…」那条备用路——
**不要假装成功**，否则用户看到的就是「点了没反应」。

## 只接受本机页面的请求

服务没有认证，谁能发 HTTP 谁就能让它读写文件。以前它只服务一个启动时指定的目录，
现在它能打开这台机器上的任意目录，所以这道门必须在放开那条路之前就关上（`LocalOnly`）：

- **`Origin` 不是本机就拒绝**——你浏览别的网页时，那个网页的脚本可以往 `127.0.0.1` 发请求。
  它读不到响应（跨域），但副作用——改文件、跑一次模型——是实打实的。
- **`Host` 不是本机也拒绝**——攻击者让自己的域名解析到 `127.0.0.1` 时，浏览器以为是同源，
  这时 `Origin` 和 `Host` 都是那个域名，只看 `Origin` 挡不住。

## 界面为什么用轮询而不是 SSE
这里真正的延迟在模型调用上——一次几秒。400 毫秒的轮询延迟根本感知不到，
而它换来的是一条没有长连接、没有分块编码、刷新页面就能恢复的普通 HTTP 请求。

`RunHub` 只做三件事：存事件、给事件编号、按游标返回增量。
`runId` 是给界面的护栏：带着上一次的游标来问、而服务端已经开了新一轮时，
界面凭 `runId` 不一致就能发现并从头拉，而不是默默漏掉开头几条。

并发被直接拒绝（409）：两个 Agent 同时改同一批文件，快照和回滚会互相踩。

## 已知的取舍

- **不做自动挑相关文件。** 检索错文件比不检索更危险——模型会照着错误的上下文
  写出一份自洽的错代码。当前是让 spec 显式列 targets，文件太多直接报错。
- **目标文件总量超预算时报错，不截断。** 悄悄截断会让模型基于半份文件写锚点。
- **失败留下的快照目录不自动清理。** 它是排查现场，最后一轮的快照会保留在
  `.specflow/snapshots/<时间戳>/`，里面有改前原文和清单。
- **没有 dry-run。** 界面上的「运行」是直接写盘的。`validate` 覆盖了 spec 层面的错误，
  补丁全量校验在落盘前完成，但没有任何一步会先停下来问「这样改行不行」。
  界面里的文件差异面板是**改完之后**的展示，不是改之前的预览。这是下一个该补的功能。
- **写入不是原子的。** 直接截断重写目标文件；写入中途进程被杀会留下半个文件。
  可靠性由快照兜底（`.specflow/snapshots/<时间戳>/files/` 里有改前原文），
  而不是靠文件系统原子替换——后者在不同平台上的行为差异会带来新的坑。
- **混合行尾的文件会被统一。** 写回时按「出现任一 CRLF 即整文件用 CRLF」的规则统一，
  这是为了让规则可预测；代价是混合行尾的文件会被规范化。
- **追溯锚点由模型写。** `trace` 段会被拼进提示词并要求模型插入 `@requirement`
  注释，引擎不在事后改写文件——避免出现「校验通过的字节 ≠ 最终字节」。
- **模板名即文件名，源码视图里改 `name:` 会被拒绝。** 也可以选择「按新名字另存一份」，
  但那是**静默**多出一个模板：用户可能只是想改个备注却打错了一行，回头发现列表里
  凭空多了一个。改名的唯一入口是表单里的「名称」，那里本来就标着「同时是文件名」。
  拒绝的理由必须说清楚，否则用户只会觉得「这儿怎么改不了」。
- **切换模板不拦未保存的编辑。** 弹层顶部下拉框切走时，表单里的内容直接丢。
  要拦就得同时判定「表单」和「源码」两个视图各自的脏状态，还要接一个确认弹窗，
  代价大于收益——「保存」按钮就在同一个弹层里。
- **模板的 `system` 里不能写占位符。** 界面上没有填变量的地方，允许就等于留一个
  「存得进去、一运行就报未赋值、而且无从修复」的死胡同。要随每次变化的内容，请写进需求。
- **`LocalOnly` 的边界依赖浏览器行为。** 不带 `Origin` 的请求按「本机上的命令行工具」放行，
  而且只看 `Origin` 里的主机名、不校验端口——也就是本机任意端口上的页面都能驱动这个服务。
  现代浏览器对跨站请求一定会带 `Origin`（包括 `null`），所以这不构成可利用的洞；
  真要收紧就得引入一个每次启动都要带上的 token，代价大于收益。
- **「已存在的文件一律不覆盖」有一个例外：空的 `project.yaml`。** 空文件和只有注释的文件
  在加载时等同于「没配过」，初始化要是也照样跳过，项目就会永远停在界面上那句
  「还没配过 specflow」——点多少次「初始化」都不变，还每次都回你一句「已生成 3 个文件」。
  空壳里没有任何东西可丢，所以它会被重建。`spec.yaml` 不适用：用户把想到的写成注释，
  那也是他的东西。同理，同名位置要是被一个**目录**占着，就说清楚让你先删掉它，
  而不是每次都假装成功。
- **文件索引按真实路径去重。** Windows 的目录联接（junction）在 Java 里不算符号链接，
  「不跟随链接」对它无效：一个指回项目根的联接就足以让遍历一层层套下去，
  文件列表变成几千条 `sub/loop/sub/loop/…`。所以每进一个目录都记下它的 `toRealPath()`，
  第二次走到同一个目录就退出来。
- **`.specflow/` 会出现在目标文件树里。** 严格说它是工具自己的状态目录，不该出现在
  「你要改哪些文件」的列表里；但它同时也放着你可能想直接打开的东西
  （`project.yaml`、模板原文），所以只跳过了 `snapshots/`（那里全是文件的旧副本），
  没有整目录跳过。运行记录多了它会是噪音，这是个已知的未处理项。
- **一份读不回来的模板只影响它自己，不再让整棵列表失败。** 以前是全有或全无，
  于是一个手滑写坏的 yaml 就能让界面「加载失败」，连 `specflow web` 都起不来——
  而删掉那个文件恰恰只能在界面里做。现在坏的那几份进 `broken` 名单、
  在界面上列出来并可删除。「坏东西要报出来，但不能拦着别人开工」，
  这条对模板目录成立；对 `spec.yaml` 之类单份输入仍然是一次失败就停下。
- **模板落盘是「临时文件 + 原子改名」，不是直接截断重写。** 多一次读回校验的开销，
  换掉两个真实事故：一份大到超过 YAML 解析上限的模板被静静写进目录（从此读不回来），
  以及两个请求同时存同名模板写出内容交错的半个文件——后者本身就会破坏语法。
- **模板列表的顺序是「按文件名」而不是「随 JVM 每次的哈希盐变」。** 界面默认选中的是
  第一项，顺序每次都变会让「第一个就是我常用的那个」失效。`Map.copyOf` 会把
  精心排好的顺序丢掉，所以这里用的是 `Collections.unmodifiableMap`。
