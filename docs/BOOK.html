0 · 它是什么

给它一个项目 + 一句需求，它自己把五站跑完；每一站都有闸，上一站没冻结，下一站连点都点不动。

① 环境声明容器、起环境、在容器里构建一次
② 探针只读地读项目，交出文件清单与 prompt
③ 用例生成可验收清单，人可改，冻结即锁定
④ 开发ReAct 在白名单内改真项目代码
⑤ 测试在副本 + 真容器里逐条验，结论写回清单
以上每一格：做完了 → 冻结 → 下一格解锁；回退会把下游一起作废

三条铁律（core/EventLog 的类注释里就是这么写的）

  1. 只有一个写者：日志、工具调用、闸、收场，全从 EventLog.append() 出去；
  2. id 恒等于行号：追加前现读行数、盖号、写一行 —— 于是"游标"和"第几条"是同一个数，重启接着数；
  3. 盘上是唯一的真相：读一律以盘上内容为准（内存里那份只是副本，用 (大小, 修改时间) 校验）。

1 · 核心认知（三层）

第一层：它是流水线，不是全能 Agent

Agent 只是流水线上那几站的"手"。站序、每站产物、站与站之间的闸都不由模型决定。 这一条是整个可解释性的来源：任何时候问"卡在哪一站、为什么卡"，都有唯一答案。

第二层：闸是纯函数

// flow/Gate.java —— 一格一个实现，签名只有这一行
String blocked(Facts facts);        // 空串 = 能做；否则就是直接给用户看的那句话

// flow/Gates.java —— 表在唯一的地方，顺序那条硬规则留在完整闸里
private static final Map<Node, Gate> TABLE = Map.of(
        Node.ENV, Gates::env, Node.PROBE, Gates::probe, Node.CASES, Gates::cases,
        Node.DEV, Gates::dev, Node.TEST, Gates::test);
为什么强调"纯"：实现里不许读盘、不许看时间、不许写事件 —— 同一份 Facts 永远给同一个答案。于是闸能被单测钉死（GatesTest 14 条）， 而界面上的"为什么还不能点"与 409 的正文是同一句话。

第三层：状态是文件，事件是流水账

<项目>/.specflow/
  project.yaml  env.yaml  local.env
  flow/current                       当前流程 id（一行文本）
  flow/<id>/flow.json                五格状态 + 每格产物
  flow/<id>/events.jsonl             统一归档日志（行号 = 事件 id）
  flow/<id>/cases.json               用例清单与结论
  flow/<id>/probe.json  summary.md
  flow/<id>/snapshot/<时间戳>.pending/   写前快照（④ 回滚用）
  flow/<id>/runs/<runId>.jsonl      逐次运行的账（BEGIN/END/STEP）
  flow/<id>/checkpoint.json          运行级断点：跑到哪、下一步干什么
  flow/<id>/env/<时间戳>/compose.yaml + compose.log
为什么这些不是理论，而是被三次事故逼出来的
  • ① 的闸问的是"宿主机能编译吗"，而容器里连 Maven 都没有 → ⑤ 自己装 Maven 烧掉 28 轮 / 15 分钟； 实测数据：60 次调用、23 次报错、34 分钟、12 条用例 0 条结论；
  • 整轮预算写死 60 轮，一条都还没开始验就被"准备阶段"吃光；
  • ① 和 ④ 的页面没有"冻结"按钮，用户活干完了却永远走不到 DONE —— 策略在代码里，页面在另一处。

2 · 顶层抽象与五条不变式

抽象类职责不许做什么
事实flow.Facts闸的输入：编译命令、环境起过没、容器能构建没、用例几条…不读盘、不判闸
闸flow.Gate ×5 + Gates 表唯一判据；顺序那条硬规则在 Gates.blocked(n,f,states)不读盘、不看时间
状态flow.FlowState五格 LOCKED/READY/DONE + 产物不判能不能动
落盘core.Atomic / flow.Store临时文件 + ATOMIC_MOVE；flow.json 原子替换不解释业务
事件core.EventLog单写者、id ≡ 行号、行快照带校验和不以内存为真相
过程core.Progress长任务的唯一过程口（step/line/warn/fail/done）不各自写文件
工具agent.Tool + ToolRegistry名字+说明+参数声明+执行体；失败是结果不是异常不碰允许根之外
循环agent.LoopReAct；轮次/工具数/输出长度/压缩四道闸不判业务闸
裁决test.CaseList + CaseBudget用例终态与证据；每用例的轮次预算不自己造用例
五条不变式（破坏任何一条都会把旧版本的坑重新挖出来）： ① 事件只有一个写者；② Event.id 恒等于行号；③ 一个事实只有一个名字（Facts 常量）； ④ Layout 是唯一路径权威；⑤ 长任务只从 Progress 一个口说话。

4 · 一次运行（执行图）

人点按钮
闸（纯函数）先判：前置没冻结 → 409 + 一句话；事件流留一条 type=gate 的账
开工
Runs.start() → Journal.begin() 写 BEGIN → Jobs.register() 登记（可叫停）→ 落第一条 checkpoint（RUNNING）
拍副本
TestSandbox.prepare()：项目树复制到 flow/<id>/sandbox/<runId>，渲染挂副本的 compose，up -d --wait
预检
Preflight.check()：容器里 command -v <构建工具>。缺 → 立刻失败、指名改 env.yaml，并把断点写成 BLOCKED
ReAct
每轮：压缩（超阈值时）→ 问模型 → 解析 → 工具 → 结果回喂。工具链外面套三层：准备宽限 + 每用例预算、打转检测、提权/装工具链/高危拦截
写结论
case_update → CaseList.settle() → 回调落 checkpoint（哪几条到终态）→ 事件流推 chip
收场
Journal.end(status) + Progress.done/fail（失败也要如实报已写几条结论）；全绿则清断点
人
提交（附总结）→ 接受（闭环）／再优化一轮（总结回喂 ④）

5 · core：地基

类一句话
Layout项目里每一样东西落在哪，只有这一处定义
Atomic写盘唯一入口：临时文件 + ATOMIC_MOVE；追加只用于事件流
EventLog单写者归档日志；id ≡ 行号；行快照按 (大小, mtime) 失效
Event一条事件：id/type/at/node/level/text/tool/args/result/callId/status/millis/round/payload
Progress / EventProgress长任务唯一过程口；实现把过程写成事件
Cmd跑一条命令：超时、逐行回调、杀整棵进程树、GBK 兜底解码
Jobs"现在有什么在跑、叫停要杀谁"
Json / Project / Llm唯一 mapper / 项目与密钥 / 模型调用口
Logs / MetricsMDC 链路 id 与脱敏 / 业务计数器

5.1 EventLog 的三段核心

public synchronized Event append(Event event) {
    Event stamped = event.withId(rows().size() + 1L);      // ① 行数 + 1 = id
    String row = Json.line(stamped);
    Atomic.appendLine(file, row);                          // ② 只追加，一次写一行
    extend(row);                                           // ③ 把行快照接上（O(1)）
    return stamped;
}
为什么"盖号"要现读行数而不是自增一个计数器：进程重启之后计数器会从 0 重来， 而界面的游标停在"第 1200 条"——两边一错位，要么重复要么漏，上一版就是这么丢历史的。 现读行数之后，行号就是唯一的号源。
private record Snapshot(long size, long mtime, List<String> rows) {}
private List<String> rows() {
    Snapshot cached = CACHE.get(file);
    long size = Files.size(file), mtime = Files.getLastModifiedTime(file).toMillis();
    if (cached != null && cached.size() == size && cached.mtime() == mtime) return cached.rows();
    List<String> fresh = List.copyOf(Files.readAllLines(file));   // 对不上就整份重读
    CACHE.put(file, new Snapshot(size, mtime, fresh));
    return fresh;
}
这算不算破掉"盘上是唯一真相"：不算。缓存的是"盘上内容的副本 + 校验和"， 校验和对不上就整份重读；谁手工改了文件、或别的进程追加了，大小/时间立刻变。 为什么必须加：界面改 SSE 之后每 250 毫秒读一次"从第 N 行到末尾"， 不缓存等于每秒把几 MB 的文件读四遍。

5.2 Atomic：为什么写盘只能从这一个口

Path temp = file.resolveSibling(file.getFileName() + ".tmp");   // 同目录：跨盘 rename 会退化成复制
Files.writeString(temp, content, UTF_8, CREATE, TRUNCATE_EXISTING, WRITE);
Files.move(temp, file, REPLACE_EXISTING, ATOMIC_MOVE);          // 要么旧的全部，要么新的全部
这一版写的是用户的真项目（改代码、写配置）。"写到一半被 kill"留下的半份文件 比没写更糟：用户打开它看到的是一份语法都不完整的文件，而没有任何地方告诉他这是崩溃留下的。

6 · flow：流程（判据与状态的唯一住处）

6.1 Facts：闸要问的 13 个问题

public record Facts(String compile, boolean envReady, boolean envNotNeeded, boolean envDeclared,
                    boolean probeFiles, boolean probePrompt, int caseCount, int casePending,
                    boolean testRun, boolean submitted, boolean compilePassed,
                    boolean containerBuild, String containerDetail) {}
最后两项是 v3 加的：containerBuild = 容器里真构建过， 与 compilePassed（宿主机编译过）是两件事——见 §12.1「两条编译」。 每个字段名在 Facts 里只出现一次（不变量 3），写的人和读的人用同一个常量。

6.2 FlowService：两个闸入口，别混

requireOpen(node, action)       // 完整闸：动作进来之前（前置没 DONE 一律 409）
requireReachable(node, action)  // 只判前置：给"这一格的活正是为了满足它自己的门槛"用
requireReachable 为什么非有不可：① 的门槛是"编译命令非空 + 环境起过"， 而"探测环境"正是产出编译命令的那一步。按完整闸判，用户第一次进来连点都点不了——自锁。 这是端到端实跑撞出来的（409 环境还没起来），不是想出来的。

6.3 FlowState 的 READY/LOCKED 是现推的

private static boolean refresh(FlowState state) {     // 只有 DONE 是记下来的
    for (Node node : Node.values()) {
        if (state.stateOf(node) == State.DONE) continue;
        Node previous = node.previous();
        State want = previous == null || state.stateOf(previous) == State.DONE ? READY : LOCKED;
        if (state.stateOf(node) != want) { state.setState(node, want); changed = true; }
    }
    return changed;
}
不推的话 GET /api/flow 报的是"上次落盘时"那个状态，而界面据此把节点灰掉， 用户点了没反应却看不出为什么。代价是每次读都读一遍 flow.json——用一次读盘换"状态不骗人"。

6.4 Journal（崩溃那本账）与 Checkpoint（跑到哪）

// Journal：判据只有一条，简单到一眼能看懂
//   有 BEGIN 而没有 END 的运行 = 被杀过
List<String> sweep();     // 启动时扫一遍，补记 END 成 INTERRUPTED，并如实报出来
为什么补 END 而不是自动回滚：自动回滚等于替用户决定"那次成果不要了"， 而它可能只差最后一步。Session.openProject() 现在每次打开项目都会调它 （这一条是审计发现的：sweep() 从 v2 就写着，却没有任何调用点）。
// Checkpoint：存"状态 + 下一步"，不存对话历史
public record Checkpoint(String node, String runId, String at, String next,
                         List<String> doneCases, int roundsUsed, String status) {}
为什么不存对话：一条工具结果最多两万字符，存下来就是第二份真相， 而且恢复时要处理"模型看到的历史和我认为的历史不一致"。断点只说三件事： 哪几条已到终态（硬的，在 cases.json 里）、下一步干什么、这一轮花了多少。 参考 LangGraph durability="exit"：只在一步做完时落一次

7 · env：环境

类职责关键设计
EnvConfigLoader读 env.yaml结构问题带行号、一次报全；未知字段报错（不是静默忽略）
Compose渲染 composeapp：uid 1000 + cap_drop ALL + 限额 + 只挂项目树 + 一个 external 缓存卷
Environmentup / reset / down / statusinit 命令走 sh -s 的 stdin；失败即 down -v 不留半成品
Compiler跑项目配的编译命令在宿主机上跑，且过 CommandGuard.forbidden
Capabilities起完环境验能力认工具 → command -v → 真跑一次构建
Budgets「这一步我愿意等多久」唯一换算处；1 分钟～4 小时夹紧
CommandGuard哪些写法不许/要问/算装工具链三档：forbidden / highRisk / privilege+bootstrap

7.1 Environment.inApp()：唯一一条"进容器"的路

public Cmd.Result inApp(String command, long timeoutSeconds, Progress progress) {
    Path file = activeCompose();
    if (file == null) return new Cmd.Result(125, "环境还没起过…", false, 0);
    Run run = new Run(progress, file.getParent());
    return run.step("在容器里跑：" + commandSummary(command),
            run.argv("exec", "-T", Compose.APP_SERVICE, "sh", "-s"), command, timeoutSeconds);
}
命令原文走 stdin 而不是 argv：Windows 上 docker.exe 会把参数里的引号吃掉一层， 用户的 SQL/脚本在容器里散架，而报错方向完全指错。宿主上被启动的程序只有 docker.exe 一个。

7.2 依赖缓存卷：数据每轮重置，依赖跨轮复用

- type: volume
  source: "sf-<项目>-<指纹>-home"
  target: "/specflow-home"
volumes:
  "sf-<项目>-<指纹>-home": { external: true, name: "sf-…-home" }
external: true 是关键：它不属于这次 up/down 的生命周期， 所以 down -v 不会把 ~/.m2 一起删掉；而项目树每轮仍是新副本。 不这么做的代价是实测过的：每轮重下依赖，7 轮 sleep 240、17 分钟白等。

7.3 Capabilities：把"能用"变成可执行

    if (!found.ok()) return new Report(tool, false, false, 0, "容器里没有 `" + tool + "`…改 image 或 init", …);
    Cmd.Result built = env.inApp(compile, timeout, progress);          // 贵的一跑
    …
}
这就是那次事故的对照实验：① 原先只在宿主机编译，宿主机有 Maven 所以绿灯； 现在 ① 会问容器——缺什么当场红，并把"改 image 还是改 init"写在话里。 参考 Temporal 的"失败分类"：先问便宜的（工具在不在），再跑贵的（真构建）

8 · agent：ReAct 与工具

8.1 Loop：一轮的原文

while (round < limits.maxRounds()) {
    round++;
    if (progress.cancelled()) return outcome(CANCELLED, …);
    lastCompact = Compact.maybe(messages, anchors.get(), limits.compactChars(), limits.compactKeepTail());
    Turn turn = turn(messages);                 // 问模型 + 认它（认不出就同轮补问两次）
    if (turn.parsed().kind() == ANSWER) return outcome(DONE, …);
    if (++toolCalls > limits.maxInstalls()) return outcome(TOOL_LIMIT, …);
    Signal signal = runTool(round, turn.parsed(), messages, calls);   // 开始→执行→结果→回喂
    if (signal != null) return outcome(DONE, "模型交差", …);
}
四条上限全在循环里，而且每一条都有自己的收场档：轮次 / 工具调用次数 / 单次输出长度 / 单次工具超时。工具坏了不崩循环——注册表把异常翻成 ok=false 喂回模型。

8.2 Compact：确定性锚点，不调模型

kept.add(messages.get(0));                                     // system：协议与规矩
kept.add(Llm.Msg.user("【压缩前的锚点】…\n" + anchors));          // 引擎按事实拼的表
kept.add(messages.get(1));                                     // 原始任务书：需求不能丢
kept.add(Llm.Msg.user("【压缩说明】不要重复已经做过的事…"));
kept.addAll(tail);                                             // 最近 keepTail 条原样保留
为什么不让模型写摘要：多一次延迟、多一次花钱、多一个故障点；而它要保住的只有三件事 ——动过哪些文件、最近为什么失败、做到哪一条，引擎自己就知道。 参考 Claude Code：三类锚点 + 双水位触发；参考 LangGraph pre_model_hook：账本 ≠ 模型视图

8.3 Tool、ToolRegistry、StuckCheck

public interface Tool {
    String name();
    String description();                  // 写给模型看：什么时候该用它
    Map<Param, …> params();                // 参数声明（缺必填就拒，不看值是不是空串）
    ToolResult run(Map<String, Object> args);
}
// StuckCheck：两级处置 —— 第 4 次只提醒，第 6 次才判死
if (same >= HARD_AT)  return ToolResult.failure("…这是卡死，不是推进。该收场了：把这条用例标 ERROR…");
if (same >= NUDGE_AT) return ToolResult.failure("…这是原地打转。换一种做法…（再连着来 2 次我就让你收场）");
return inner.run(args);
这一条对应"连着 7 轮 sleep 240 看日志"：每轮都成功、每轮都毫无进展，轮次预算拦不住它。 为什么是两级：深读 OpenHands 的 openhands/controller/stuck.py 发现它是 3 次提醒、4 次判死—— 那份研究里有句话很扎：我们原来是在最有救的那一刻把用例判死。 参考 OpenHands stuck detector（我们只做了"同一条调用重复"这一条判据，注释里写明）

8.4 Loop.grounding()：每条结果钉一行"你在哪"

messages.add(Llm.Msg.user(where.isBlank() ? body : body + "\n（当前位置：" + where + "）"));

9.1 CaseBudget：预算的粒度是"一条用例"

当前用例 = 清单里第一条还没到终态的用例；每次工具调用记在它头上
if (calls <= PREP_GRACE) return null;                 // 准备阶段有 8 次宽限，不算账
if (spentOn(which) < perCase) return null;

为什么"笨规则"要配宽限：Agent 开始验之前要先读一圈代码，那些调用如果记在第一条头上， 第一条会一秒没验就被跳过——端到端实测撞到两次才看清。 参考 Airflow 的 retries/skip 语义：跳过是终态，但不是结论

13 · 参考了谁、借鉴了什么 ★

这一章是本轮新增的：先读源码、再决定抄不抄。每条都写清「看到什么（文件:行）→ 抄了什么 → 我们改成了什么样」。 研究原文在 docs/v3/research/（langgraph / temporal / argo / claude-code / toonflow / dify / openhands / aci）。

13.1 LangGraph —— 中断与断点

看到什么抄了什么我们改成了
interrupt() 抛 GraphInterrupt 让 run 体面结束，退出时落 checkpoint， 恢复时 Command(resume=v) 变成一条 pending write，重新调度时按"节点内第 N 个调用"取值 （types.py:1019-1038、_loop.py:1033-1047,1500-1511） "把等人降级成一条状态写"这个思想 没照抄：它恢复的代价是节点从第一行整段重放（types.py:918 原文 "re-executing all logic"）， 而 ⑤ 里有 docker 副作用。我们改成每用例粒度的续跑：已到终态的用例是硬的（在 cases.json）， 恢复=只验还没到终态的那些（POST /api/node/test/resume）
checkpoint 有 durability="exit" 那一档：只在退出时落一次；存的是状态+下一步而不是历史链 这一档语义flow/Checkpoint：每写回一条用例结论落一次，存 doneCases + next + status
pre_model_hook：全量 messages 进 checkpoint，每轮只换一份压缩视图喂模型（账本 ≠ 模型视图） 这个分层agent/Compact：Loop 每轮开头按阈值压一次，锚点由调用方给
每 superstep 全量 channel_values + versions_seen 版本调度 不抄它的"下一步"要从版本差推导；我们的"下一步"由五站图 + 闸显式决定，引入=纯臃肿

13.2 Temporal —— 重试、心跳、以及"不要抄什么"

看到什么抄了什么我们改成了
RetryOptions：doNotRetry 失败分类 + 退避（initialInterval/backoffCoefficient） "重试前先分类"这条 disciplineApproval.Decision 三态 + ToolResult 的"永久失败"不再重试； 退避暂未加（toolAttempts 默认 1，没触发过）
四种超时（Schedule-To-Start/Start-To-Close/Schedule-To-Close/Heartbeat）；心跳=由外部时钟裁定"还活着吗" 心跳与"内容猜测"的本质差别StuckCheck（内容判据）只覆盖"调用返回后"； 命令执行期间的判死由 Loop.once() 的 worker.join(timeout) 覆盖
确定性 replay 全套（NonDeterministicException、sideEffect、isReplaying） 明确不抄我们存的是"已落盘的副作用结果"，存结果就不需要确定性。 研究报告里的一句话很准：我们已经付了 replay 的 90%（事件流 id≡行号 + callId 成对 + BEGIN/END）

13.3 Argo Workflows —— 失败语义与"流程该不该 YAML 化"

看到什么抄了什么我们改成了
RetryStrategy.retryPolicy 把失败切成 Failed（跑了但结果不对）与 Error（根本没跑起来），默认只重试 Failed（operator.go:1218-1237） 这个两轴我们的"镜像拉不下来/白名单拒绝"属 Error，不该重试—— 体现在 Preflight 与 CommandGuard 的"立刻失败"上
backoff.maxDuration 是从第一次尝试起算的截止时刻（retry.go:15-16） 这个语义env/Budgets：界面一个分钟数，起环境/构建/容器/命令全从它来
关于"把流程做成 YAML"不抄（研究结论比我原来的方案更强） 它指出我们真正的问题不是"没有 DSL"，而是节点定义有 6 个落点（Node 枚举 / Gates 表 / Api 路由 / 前端 flow.js / pages.js / 各视图动作数组）。加一份 YAML 是第 7 个落点。正解是把前端那几张表压成 GET /api/flow 下发的一份 —— 这条列入待办，见 §15
它最狠的一句："最该补的不是重试，是收尾"（onExit 零命中）这个审计 顺着这句查我们自己的代码：Journal.sweep() 与 FlowService.close() 定义了却没有任何调用点 → 本轮接上（Session.openProject() / closeQuietly()）

13.4 Claude Code 生态 —— compact 与 hooks

看到什么抄了什么我们改成了
compact 用纯 token 算术（窗口−20K 输出预留；再 −13K buffer ≈93% 触发、−3K 硬阻断）， 保留三类锚点：当前任务（权威）/ 最近 3 条 tool_result 且不切开配对 / 最近 touch 的文件 三类锚点 + 双水位思想Compact.DEFAULT_CHARS=60000（单阈值，够用就不加第二个数）； 锚点由 TestAgent 给：动过的路径 / 最近失败 / 当前用例与已用轮次
27 个 hook 事件 + 四种 hook 类型 + exit-code 协议（单 execCommandHook() 590 行） 不抄它是为"用户从 settings.json 注入脚本"的生态服务的，不是 agent 正确性所需。 我们的 Frozen/CaseBudget/StuckCheck 三个装饰器等价覆盖了同样能力
连续 3 次被拒 → 熔断升级问人；连续 3 次压缩失败 → 停（线上实测有 session 连续失败 3272 次） 熔断的想法暂未做；Approvals 的超时按拒 + StuckCheck 已覆盖一部分

13.5 toonflow —— 用户点名，结论和我预期相反

它存在（HBAI-Ltd/Toonflow-app，约 1.8 万 star，TypeScript，MIT），但不是工作流引擎： 全仓库没有 executor/pipeline/DAG；"可视化工作流"实际是数据依赖图（边只表示 output→input）， "执行"是 Vue computed 重算；流程定义是一份 1406 行的 Markdown 提示词，不是 DSL。

但它有一点正好治我们的病：节点动作只有一份定义，后端没有副本——后端只解析节点包第一行注释里的元数据， 连"这节点有哪些输入口"都不知道；能力由组件运行期自己注册成工具，schema 由 Zod 自动生成。 加一个节点 = 加一个包，后端零改动。

所以我们的结论：要学的不是"它的编排"，而是"同一份定义只存在一处"。对应到我们： 把前端的节点/动作表压成后端下发的一份（GET /api/flow 已经是天然出口）。

明确不抄：1406 行提示词当流程引擎（它自己文件里 60+ 行反复加"硬隔离/禁止"，就是证据）， 以及它依赖单进程内存的回传通道。

13.6 其余（研究仍在跑或本轮未深入）

  • Dify：节点基类 + 注册表、SSE 事件清单、变量池——我们对齐了"SSE 推进度"这一条，其余未抄（我们没有几十种节点类型）。
  • OpenHands：stuck detector 判据、Runtime 抽象——只抄了 stuck 的第一条判据。
  • SWE-agent / Aider：ACI 原则、history processors——落到"工具少而专 + 错误写给模型看 + 压缩保留锚点"。
  • 12-factor agents：自有控制流、compact errors into context、launch/pause/resume——落到"五站写死 + 错误全文回喂 + 断点"。

15 · 明确没做的

  • 流程 DSL（flow.yaml）没做——不是没时间，是研究结论认为它会是"第 7 个落点"。 真正该做的是把前端那几张表压成后端下发的一份（待办）。
  • 工具中间件链（ToolHook）没做——Claude Code 的 27 事件 hook 体系是给"用户注入脚本"的生态， 不是正确性所需；我们的三个装饰器已等价覆盖。要做的只是"装饰器返回值从 boolean 升级成四值枚举"（待办）。
  • 跨重启的可恢复中断（把对话历史落盘再接着跑）没做——上面 §13.1 已说明为什么：它要求把两万字符一条的工具结果也落盘， 那是第二份真相。我们选了"用例粒度的续跑"，覆盖 90% 的真实场景。
  • Api 层没有单元测试：项目没引 spring-boot-starter-test；覆盖靠浏览器冒烟 + SSE curl + 端到端。
  • 审批的超时分支没实测：问→答→执行→写回已在真跑里走通（最后一次端到端 `替你点了 1 条审批`），但"人不在、等满 2 分钟按拒"只有单测覆盖。
  • 界面没有逐页视觉走查：我看不到图（模型不接图像输入）。
