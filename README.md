# specflow

规格驱动的代码修改 Agent。

模型只负责「想改什么」，落盘这件事由本地引擎按固定规则完成：
精确匹配、唯一性校验、重叠检测、快照回滚、编译自检。
模型给错锚点就报错重来，不会静默改错文件。

---

## 快速开始

```bash
mvn -q package

java -jar target/specflow.jar init            # 在某个项目里生成 .specflow/ 与 spec.yaml 骨架
java -jar target/specflow.jar web             # 浏览器界面（推荐）：先进欢迎页挑项目
java -jar target/specflow.jar web -p <目录>    # 跳过欢迎页，直接打开这个项目
```

Windows 上直接双击 `启动界面.bat`：没有 jar 就编译、缺密钥就问一次并记住、端口被上一次的
残留实例占着就先收掉，然后起服务并打开浏览器——进去是欢迎页。

**密钥**只认两个地方，环境变量优先：

```bash
export SPECFLOW_API_KEY=sk-...      # Windows: set SPECFLOW_API_KEY=sk-...
```

```properties
# .specflow/local.env —— 写一次，往后每次启动都不用再输
SPECFLOW_API_KEY=sk-...
```

不放进 `spec.yaml` 之类是要进版本库的配置里；`local.env` 在 `.gitignore` 里。

`web` 会起一个只监听本机的服务并自动打开浏览器。**进去先是欢迎页**：左边是最近打开过的项目，
右边「打开文件夹」能翻目录挑一个（它会告诉你那个目录是什么项目、建议用什么编译命令）。
打开之后左边勾选文件、中间写需求、右边实时看到「第几轮在干什么 / 编译过没过 / 改了哪几行」。
**换项目随时可以**，右上角「切换项目」就回欢迎页。命令行那一套还在，两者跑的是同一套引擎。

一个服务同时只服务一个项目，切换是全局的——**不是每个标签页各一个**。
有任务正在跑的时候不许切：换掉之后那次运行会把文件写到旧项目，等于白跑一趟还留一地垃圾。

## 打开一个项目会做什么

打开任意目录都行，**只读扫描，不往它里面写任何东西**：

| | |
|---|---|
| 打开目录 | 点「打开文件夹…」**弹出 Windows 自己的文件夹选择窗口**，像 IDEA 打开项目一样 |
| 认清单文件 | `pom.xml` / `package.json` / `go.mod` / `CMakeLists.txt` … 认得出来就告诉你这是什么项目 |
| 猜编译命令 | 有 `mvnw` / `gradlew` 就**优先用 wrapper**（那是项目自己声明的版本），没有才用系统上的 |
| 记住它 | 写进 `%USERPROFILE%\.specflow\projects.json`，下次在欢迎页一眼能找到（同一个目录的大小写、短名等不同写法只记一条） |

**那个弹窗为什么不是页面弹的**：浏览器出于隐私不会把系统对话框里选中的**绝对路径**交给页面
（`<input webkitdirectory>` 和 File System Access API 都只给文件名）。所以由跑在同一台机器上的
这个服务去弹——它弹的窗口就出现在你的桌面上，选完路径直接拿回来。
服务要是跑在没有桌面的环境里（比如当后台服务起），弹不出来会明确告诉你原因，
下面还有一条「手动输入路径…」可以走。

**认不出来也照样能打开**，只是没有编译校验、也没有针对这个项目的模板。

配置坏了不会把你锁在门外：**空的和只有注释的 `project.yaml` 都当作「还没配过」**，
项目照样打得开，点「初始化」就能修好。「最近打开」里有一条坏记录也只影响那一条
（显示成「已不在磁盘上」，右边仍然可以把它删掉），不会让整个欢迎页打不开。

目录里还没有 `.specflow/` 时，工作区顶上会说清楚，并给一个「初始化」按钮——
它生成 `.specflow/project.yaml`（编译命令按上面扫出来的填）、两个模板、一个示例 `spec.yaml`。
**已存在的文件一律不覆盖**，而且是在你点了之后才写；唯一的例外是一份空的 `project.yaml`
（见上面那句）。

```bash
java -jar target/specflow.jar validate        # 只校验 spec，不调用模型、不花钱
java -jar target/specflow.jar run             # 命令行方式运行
```

五条命令：

| 命令 | 做什么 | 会不会改文件 |
| --- | --- | --- |
| `web` | 启动浏览器界面，Ctrl+C 结束 | 点「运行」才改 |
| `init` | 生成 `.specflow/project.yaml`、两个模板、示例 `spec.yaml`（已存在则跳过） | 只新建骨架 |
| `validate` | 校验 spec 语法、语义、模板能否加载 | 不会 |
| `templates` | 列出可用模板及其需要的变量 | 不会 |
| `run` | 调用模型 → 校验补丁 → 落盘 → 编译自检 | 会，失败自动回滚 |

`run` 的退出码：`0` 成功 · `1` 失败（磁盘已回滚）· `2` 模型要求补充信息（磁盘未动）。

## Web 界面

```
java -jar target/specflow.jar web [--port 8770] [--no-open]
```

- **目标文件**：可折叠目录树，勾选即可；不在树里的路径（要新建的文件）手输
- **模板**：选一个模板就按它声明的 `fields` 渲染出表单，类型标签、默认上下文一起带进来
- **上下文依赖**：引用项目里的文件（每次运行实时读取）或粘贴一段文本，逐条可增可删
- **先检查**：让模型先交一份**实现方案**——Mermaid 流程图 + 缺失依赖清单，你确认了再开发
- **结果**：每个文件一个可展开的差异面板，`-` 红 `+` 绿

服务只绑定回环地址，不是可配置项——它能读写你项目里的文件，暴露到局域网就等于把改代码的权限交出去。

界面和命令行共用同一套校验与落盘逻辑：界面提交的表单会被转成同一个 `Spec` 对象，
走同一个 `SpecValidator` 和同一个 `PatchStrategy`。所以两边拒绝补丁的理由永远一致。

### 先检查，再开发

```
选模板 → 填需求 → 选目标文件 → 组装上下文
                                    ↓
                              [ 先检查 ]      ← 一次独立调用
                                    ↓
                     流程图 + 缺失清单（可丢弃、可重新检查）
                                    ↓
                              [ 运 行 ]        ← 确认过的流程图作为施工图回喂
                                    ↓
                     出补丁 → 校验锚点 → 写盘 → 编译 → 不过就回滚重来（上限 6 轮）
```

检查阶段和开发阶段看到的是**同一份上下文**——目标文件的当前内容、上下文依赖、需求，
一模一样。变的只有最前面那段协议：一个问「你打算怎么做」，一个说「把代码交出来」。
这一点很关键：检查时不给它看目标文件，判断就是悬空的，而它后面写锚点也离不开这些内容。

流程图由模型写成 Mermaid（它训练数据里最多的图表格式，输出最稳），但**不引 mermaid.js**——
引擎只解析一个很小的子集，用 SVG 自己画，零依赖、离线可用。解析不出来就直接显示源码兜底。

**跳过检查直接运行也完全可以**，它是可选的加速器，不是关卡。

## spec.yaml

一次改动的完整契约。

```yaml
version: 1

strategy: search_replace    # 目前只有这一种；留作扩展点

template: spring-backend    # 可选。只给角色与标签，不给需求

prompt: |                   # 必填。这次要做什么，随便写
  给 Console 加一个 error 方法，输出以 "[ERROR] " 开头的行

acceptance:                 # 可选。怎样算做完
  - 不比 ok/warn/fail 更晚输出
  - 不改动已有方法的签名

# 允许改动的文件白名单，必填。
# 文件不存在就是新建，已存在就是就地修改——不用声明模式。
targets:
  - src/main/java/com/specflow/cli/Console.java

constraints:                # 给模型的额外约束，可选
  - 不引入新的第三方依赖

context:                    # 上下文依赖，可选
  - ref: src/main/java/com/demo/UserController.java   # 引用文件：每次运行实时读取
    note: 照这个已有接口的风格写
  - name: 订单表结构                                   # 或者粘贴一段文本
    text: |
      CREATE TABLE orders (id BIGINT, status VARCHAR(16))
    note: 库里的真实定义

verify:                     # 落盘后的自检，可选
  compile: true             # 默认 true
  compile-command: null     # 覆盖 project.yaml 里的编译命令
  max-retry: 6              # 编译失败后携带报错重试几次，默认 6

trace:                      # 追溯信息，可选
  requirement-id: R-001
  acceptance-criteria: [AC-1]
```

拼错字段名会直接报错并列出可用字段，不会静默忽略。

## .specflow/project.yaml

项目级的、固定的配置。

```yaml
build:
  compile: "mvn -q -DskipTests compile"   # 留空则跳过编译校验
llm:
  base-url: "https://api.deepseek.com"
  model: "deepseek-chat"
  api-key-env: "SPECFLOW_API_KEY"         # 去哪个环境变量取密钥；取不到会再看 .specflow/local.env
  temperature: 0.2
snapshot:
  enabled: true                           # 落盘前做快照，失败自动回滚
  dir: ".specflow/snapshots"
```

## 模板

模板放在 `.specflow/templates/*.yaml`，文件名即模板名。

**模板只装「项目那一侧的常量」——产物形态、技术栈、角色、代码风格、常用的参考文件。**

```yaml
name: spring-backend
tags: [class, java, spring-boot, mybatis]   # class 是产物形态，其余是技术栈；引擎不区分
description: Spring Boot 后端通用模具
system: |                                   # 角色、做法、边界
  你是一名严谨的 Java 后端工程师。
  你只修改需求所要求的部分：不要顺手重构，不要调整无关代码的格式。
context:                                    # 默认依赖，本次可逐项移除
  - ref: src/main/java/com/demo/UserController.java
    note: 照这个已有接口的风格写
```

**它不装需求**——需求、验收标准、目标文件、本次补充的上下文，全部属于运行时。
写进模板，就等于「一个模板只能匹配一种需求」。
一个「Spring Boot 后端」模具可以用于加接口、加方法、改逻辑、修缺陷，不用给每种需求各配一个。

**`tags` 只写框架名就够了**——写了 `mybatis`，模型自己就知道有 `@Select` 这类注解。
标签里既有产物形态（`class` / `function` / `script`），也有技术栈，引擎不区分这两层，
一律拼成一段话，并补上一句优先级声明：

```
## 模板约定
class、java、spring-boot、mybatis

产出物的形态与技术栈以上面这组约定为准，可以直接使用其中的注解与标准封装类；
但具体的设计细节以本次需求说明为准。
```

标签管「可以用什么」，需求管「要什么」，冲突时以需求为准。

内置两个种子模板：`spring-backend`（后端通用模具）、`修缺陷`（按现象定位缺陷）。
种子只是 `specflow init` 铺的两个起点，**不是上限**——在模板下拉框里选「＋ 新建模板…」，
或者点「管理模板 → 新建」，就能加自己的，比如一个「接口」模板配上
`interface` / `java` / `spring-boot` / `mybatis`。

**手写坏了也不会把界面弄死。** 模板是文本文件，一个手滑就能写坏。读不回来的那几份会被
跳过、在界面里列出来（附上原因和一个「删除」按钮），其余模板照常可用，
`specflow web` 也照常启动。**不然就成了死结**：界面起不来，而删掉那个文件正是界面该干的事。

**写的时候是原子的。** 先写同目录的临时文件、读回来确认能用，再改名盖上去。
所以既不会出现「存进去就再也读不出来」的模板，也不会因为两个请求同时存同一个名字
而写出内容交错的半个文件。

模板的完整字段参考、标签规则、常见错误见 **[docs/TEMPLATE.md](docs/TEMPLATE.md)**。

## 它是怎么保证不乱改文件的

一次 `run` 里，模型每次输出的补丁都要过四道关，任何一道不过就拒绝落盘：

1. **路径在白名单内** —— 补丁块只能指向 `targets` 列出的文件，且不能越出项目根目录
2. **锚点存在** —— SEARCH 段落必须逐字命中目标文件的现有内容（自动抹平 CRLF/LF 差异）
3. **锚点唯一** —— 一次命中才算数；命中两处就报错，不猜该改哪一处
4. **区间不重叠** —— 同一文件的多处改动互不相交

四道关全过之后才是「两阶段提交」：先把所有改动算成一份计划，再统一写入。
写之前做快照；写之后跑编译 —— 编译不过就**回滚到运行前**，把编译错误喂回模型重来。

回滚先于重试是这里最关键的一个决定：它保证每一轮的起点都是「需求 + 原始代码」，
模型每轮都可以按原文件写锚点，不必自己追踪「上一轮改到哪了」——而这恰恰是模型最不擅长的事。

更多细节见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)。

## 测试

```bash
mvn test                                   # Java 用例

node src/test/js/web.test.js               # 前端纯逻辑：流程图解析、模板下拉框的选中规则、模板转 YAML

# 浏览器闭环：真的开一个 Chrome 把界面点一遍
java -jar target/specflow.jar web --port 3081 --no-open -p .
node src/test/js/browser.test.js http://127.0.0.1:3081/ .   # 最后那个参数是项目根
```

Java 侧覆盖：补丁解析、锚点定位规则、两阶段提交、快照回滚、模板渲染与标签契约、
路径守卫、上下文两种形态与预算、检查结果的解析、编译校验的命令来源、
Agent 的重试与回滚编排、Web 接口的端到端契约。模型与校验器在测试里都是脚本化的假实现，不联网。

前端那两份没有接进 mvn——那需要为 Maven 引入一个执行 Node 的插件，对只有两个前端文件的项目来说
代价大于收益。

- `web.test.js` 直接从 `index.html` 和 `flowchart.js` 里抽出真源码执行，测的不是副本。
- `browser.test.js` 用 CDP 驱动本机 Chrome（Node 22+ 自带 WebSocket，不用装任何 npm 包），
  走完整条链路：新建模板 → 保存 → 改 → 源码视图 → 删除，外加任务草稿的存/取/载入。
  它自己清理建出来的东西，跑完磁盘上不留痕。

**为什么要有浏览器这一层**：界面上最容易坏的地方全在「点了之后发生了什么」——
异步初始化回来晚了会把用户已经打进去的内容擦掉、报错画在了弹层背后、
点了没反应其实后端已经回了 400。这些纯逻辑测试和接口测试都看不见。
